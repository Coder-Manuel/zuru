# Zuru World — Technical & Organisational Security Measures

**Prepared for:** Office of the Data Protection Commissioner (ODPC), Kenya
**Purpose:** Registration under the Data Protection Act, 2019
**Version:** 2.0 — 21 August 2026
**Scope:** This document describes security measures **currently implemented** in
the Zuru World mobile application and its supporting backend.
Items marked **[CONFIRM]** await organisational sign-off.

---

## 1. System overview

Zuru World is a mobile marketplace application (iOS and Android) connecting two
categories of users:

| Role | Description |
|---|---|
| **Client** | Posts a location-based "mission" and pays for it, then watches it fulfilled via live video. |
| **Scout** | Accepts nearby missions, travels to the location, and streams live audio/video to the client. |

The platform is a single Flutter application with a role-switching model. Every
operation carrying security or financial consequence — payment initiation,
stream authorisation, mission acceptance, proximity matching — executes
**server-side**, not on the handset.

### 1.1 Architecture and sub-processors

| Layer | Provider | Function | Hosting region |
|---|---|---|---|
| Database, authentication, object storage, realtime, serverless functions | **Supabase** (PostgreSQL) | Primary data store and identity provider | **[CONFIRM]** |
| Push notification delivery | **Google Firebase Cloud Messaging** | Mission and payment alerts | Google global infrastructure |
| Crash and stability reporting | **Google Firebase Crashlytics** | Diagnostic stack traces | Google global infrastructure |
| Live audio/video transport | **LiveKit** | Real-time mission streaming | **[CONFIRM]** |
| Product analytics | **Mixpanel** | Pseudonymous usage events | **[CONFIRM]** |
| Mapping and geocoding | **Google Maps Platform** | Client-side location picker | Google global infrastructure |
| Turn-by-turn navigation (Scout role) | **Mapbox** | Route guidance to mission location | Mapbox global infrastructure |
| Mobile money collection | **Safaricom M-Pesa (Daraja API)** | STK Push payment collection | Kenya |

## 2. Categories of personal data processed

| Category | Data elements | Source | Applies to |
|---|---|---|---|
| **Identity** | Email address, mobile phone number, first and last name | Provided at sign-up | All users |
| **Authentication** | Password (stored only as a salted hash by the identity provider), one-time codes, OAuth identifiers from Google / Apple Sign-In | Data subject / identity provider | All users |
| **Profile** | Profile photograph, biography, service tags, spoken languages, stated locality | Provided by data subject | Primarily Scouts |
| **Media** | Short self-recorded profile video clips | Provided by data subject | Scouts |
| **Location** | Approximate locality coordinates; and, for Scouts, precise GPS coordinates sampled while the app is in the foreground | Device GPS, with OS-level consent | Scouts (precise); Clients (mission pin only) |
| **Transactional** | Mission records, payment records, M-Pesa transaction references, statements | Generated by the platform | All users |
| **Reputation** | Ratings, review counts, fulfilment rate, average response time | Generated by the platform | Scouts |
| **Live media** | Real-time audio and video streamed during an active mission | Device camera and microphone, with OS-level consent | Scouts (capture), Clients (view) |
| **Device / technical** | Push notification token, device model and OS version, crash stack traces, pseudonymous analytics events | Device | All users |

**No payment card data, PIN, bank account number, or national identity number is
collected, transmitted, or stored by Zuru World.** Payment authorisation occurs
entirely on the data subject's own handset within the Safaricom M-Pesa STK Push
prompt; the platform receives only a transaction reference and a status.

**No special-category data** (health, biometric identifiers, religious or
political affiliation, sexual orientation) is collected. Biometric
authentication is device-local — see §3.2.

## 3. Technical security measures

### 3.1 Identity and access management

- Authentication is delegated to a managed identity provider (Supabase Auth).
  Passwords are never stored in plaintext by the platform and are never written
  to application logs.
- Supported sign-in methods: email and password; Google Sign-In and Apple
  Sign-In via cryptographically signed ID tokens; and one-time-password
  verification.
- **Email ownership is verified by OTP** before an account becomes active.
  Phone numbers are separately verified by SMS OTP.
- Password reset is a **verified OTP exchange** — a code is sent to the
  registered email address, exchanged for a short-lived recovery session, and
  only then may a new password be set. Codes are single-use and time-limited.
- Sessions use short-lived JSON Web Tokens with silent refresh. Sign-out revokes
  the session and clears all locally cached identity material.

### 3.2 Device-side protections

- **Biometric unlock** (Face ID, Touch ID, Android fingerprint) is offered as an
  optional convenience. The biometric template never leaves the device's secure
  enclave and is never transmitted to or accessible by Zuru World — the
  operating system returns only a pass/fail result.
- Where biometric sign-in is enabled, the cached credential is written to the
  **iOS Keychain** or the **Android Keystore-backed encrypted store**
  (`EncryptedSharedPreferences`), never to plain application preferences.
  Disabling biometrics wipes the cached credential immediately.
- Non-sensitive state (theme, onboarding flag, cached exchange rates) is held in
  ordinary application storage, isolated per-application by the operating system
  sandbox on both platforms.
- Sign-out clears every local storage key in a single operation.

### 3.3 Transport security

- **All network traffic is TLS-encrypted.** No cleartext HTTP endpoint is
  configured on either platform, and certificate validation is enforced in all
  production builds. Certificate relaxation and verbose request logging exist
  only in debug builds, which are excluded from release artefacts at compile
  time.
- Live audio and video are transported over WebRTC with DTLS-SRTP encryption.

### 3.4 Server-side authorisation

- **Row-Level Security is enabled on every application table.** Database access
  is mediated by policies evaluated against the caller's authenticated identity
  (`auth.uid()`), so authorisation is enforced by the database rather than by
  application code alone.
- **Financial records are participant-scoped and read-only to clients.** The
  `payments` table permits reads only to the payer or the payee, and permits no
  client-side writes whatsoever — payment rows are written exclusively by
  server-side functions holding the service role.
- **Administrative operations are unreachable from the mobile client.** Creation
  and deletion of user records are restricted to the `supabase_admin` role.
- **Write access is ownership-scoped.** Users may modify only records belonging
  to them: a user may update only their own account and profile row, insert and
  manage only their own profile media, submit ratings only under their own
  identity, and create missions only under their own client profile.
- **Scout mission events are private to the Scout concerned**, readable only by
  the profile they relate to.
- Sensitive operations are implemented as **server-side Edge Functions**, so the
  handset cannot forge them:
  - `mpesa-stk-push` — initiates payment collection; M-Pesa credentials exist
    only in the server environment and never in the mobile binary.
  - `go-live` — mints a short-lived, mission-scoped streaming token, so a Scout
    cannot open a stream for a mission they are not assigned to.
- Proximity matching, mission acceptance, and location updates run through
  controlled database functions (`get_nearby_scouts`,
  `get_missions_within_radius`, `accept_mission`, `update_scout_location`)
  rather than exposing raw coordinate tables to the client, so users receive
  proximity results without direct access to other users' coordinate records.
- Role-based navigation guards prevent a Client from reaching Scout-only
  surfaces and vice versa, as a defence-in-depth layer above the database
  policies.

### 3.5 Transaction integrity

- Mission creation and payment initiation carry **idempotency controls**, so a
  retried or duplicated request cannot produce a double charge or a duplicate
  mission.
- A **`published_at` gate** ensures an unpaid mission is never visible to
  Scouts; a mission enters the marketplace only once payment is confirmed
  server-side.
- Payment status is observed through an authenticated realtime subscription
  filtered to the single payment record belonging to the caller.
- Stale missions are expired automatically by scheduled server-side logic.

### 3.6 Secrets management

- No API key, token, or credential is committed to source control. Environment
  files are excluded by `.gitignore`; the repository contains only a placeholder
  example file.
- Application keys are injected at **build time** as compile-time constants
  supplied by the CI environment, and are separated into distinct staging and
  production sets.
- Third-party secrets carrying financial consequence (M-Pesa consumer key and
  secret, LiveKit API secret) exist **only in the server-side function
  environment** and are never shipped inside the mobile binary.
- Android release signing keys are held outside the repository.

### 3.7 Data minimisation by design

- Runtime permissions are requested **only at the point of need**, each with a
  plain-language purpose string shown to the user before the OS prompt:
  - Location — "to show nearby missions and pin your map location"
  - Camera and microphone — "to stream live video during active missions"
  - Photo library — "to set your profile picture and World Profile clips"
  - Face ID — "to authenticate you quickly"
- Precise Scout location is sampled only while the application is in the
  foreground, and collection is **suspended automatically** when the app is
  backgrounded or closed. A 30-metre movement threshold prevents redundant
  collection while stationary.
- Analytics events are pseudonymous, keyed to an internal identifier rather than
  to contact details, and analytics are **disabled entirely in non-production
  builds**.
- The application requests no permission it does not use: no contacts, calendar,
  SMS, call log, or background-location access is declared on either platform.

### 3.8 Monitoring and secure development

- Crash and exception reporting is centralised through Crashlytics, supported by
  an internal monitoring service that captures handled errors with contextual
  metadata, giving early detection of anomalous behaviour in production.
- Changes are delivered through pull requests subject to **automated CI checks,
  static analysis, and an automated test suite** before merge.
- Environments are separated: staging and production use distinct backend
  projects, distinct credentials, and distinct datasets.
